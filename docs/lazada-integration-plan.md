## Application and endpoints

Lazada calls the application credentials **App Key** and **App Secret**. The App Key identifies the application and is a common request parameter. The App Secret signs requests and must remain server-side. An access token belongs to the App Key that issued it; tokens generated by another App Key are not interchangeable.

For Ecomkit's internal seller-order-management use, the official app-category guide describes **Seller In-house APP** as the category for seller-store order/product/finance/fulfilment integrations. The operator must still confirm availability, approval status, and exact permissions in the Lazada console before a live stage.

## Signing contract

Lazada requires its own signer; the Shopee signer must not be reused.

1. Include all non-binary system and business parameters except `sign`.
2. Sort parameter names in ASCII order.
3. Concatenate each parameter name immediately followed by its value.
4. Prefix that string with the API path, for example `/order/get`.
5. For requests with a body, append the body after the parameter string.
6. Compute HMAC-SHA256 with the App Secret over UTF-8 bytes.
7. Encode the digest as **uppercase hexadecimal**.

Common parameters are `app_key`, `timestamp`, `sign_method`, and `sign`; `access_token` is conditional and is required for seller-authorized business APIs. The documented `sign_method` value for HMAC-SHA256 is `sha256`. Timestamp may be UTC text or a digital timestamp; official examples use Unix milliseconds, and the difference from UTC must not exceed 7200 seconds. Ecomkit should standardize on Unix milliseconds and inject the clock for deterministic signer tests.

## OAuth and token lifecycle

The seller authorization URL is:

```text
https://auth.lazada.com/oauth/authorize
  ?response_type=code
  &force_auth=true
  &redirect_uri=<registered callback>
  &client_id=<App Key>
```

`client_id`, `redirect_uri`, and `response_type=code` are required; `force_auth=true` is optional. The redirect URI must equal the callback configured in Open Platform. The authorization code is valid for **30 minutes** and is single-use.

`/auth/token/create` exchanges the code and returns fields including `access_token`, `refresh_token`, `expires_in`, `refresh_expires_in`, `country`, `account_platform`, and `country_user_info`. Token lifetime is application-policy/status dependent; runtime must trust the returned durations rather than hardcode a universal lifetime.

`/auth/token/refresh` takes the latest refresh token and returns a new access token and refresh token. Ecomkit must atomically replace the latest refresh token. The access-token duration resets; the remaining refresh-token duration does **not** reset. When refresh expiry reaches zero, seller authorization is required again.

## Seller/store identity

Official token data identifies authorized country stores through `country_user_info`, including `country`, `user_id`, `seller_id`, and `short_code`. A token normally corresponds to one store, while a cross-border authorization can include multiple country entries.

Phase 1 candidate mapping:

- Select the `country_user_info` entry whose country is `vn`.
- Use that provider-issued `seller_id` as the store identity input.
- Persist a region-qualified external identity such as `vn:<seller_id>` in `MarketplaceConnection.externalShopId` unless live fixtures prove seller IDs are globally unique across ventures.
- Keep `seller_id`, `country`, and `short_code` as provider metadata; never use account email as the identity.

The region qualification is an Ecomkit collision-prevention convention, not a claimed Lazada field format. It must be finalized against a synthetic token fixture before connection persistence is implemented.

## Order retrieval and identity

`GetOrders` (`/orders/get`) lists orders for the authorized store. The official order tutorial confirms `created_after`, `status`, `limit`, and `offset`; `status=all` obtains all item-status combinations, `limit` is at most 100, and `offset` is at most 5000. It also links the authoritative API reference for additional parameters.

The current API reference is expected to expose bounded create/update filters (`created_after`, `created_before`, `updated_after`, `updated_before`) and sorting controls, but Stage 14D.1 could not obtain a stable server-rendered parameter table for those additional fields. Consequently:

- `created_after` is VERIFIED.
- `created_before`, `updated_after`, `updated_before`, `sort_by`, and `sort_direction` are **UNVERIFIED** pending API-console/reference capture.
- No incremental algorithm may be implemented until both update bounds and their inclusivity/timezone semantics are verified.

`order_id` is unique only within the current store. Ecomkit mapping is therefore:

- `marketplaceOrderId = String(order_id)` within its connection;
- `rawOrderCode = String(order_id)`;
- canonical `Mã đơn sàn = String(order_id)`.

There is no fuzzy identity fallback. Connection-scoped uniqueness already makes the store-local order ID safe.

`GetOrder` (`/order/get`) accepts an `order_id` and returns order-level detail. Before implementation, fixtures must establish whether `GetOrders` already contains every raw order-level field required by the normalizer; use `GetOrder` only where it adds required authoritative data, not as an unconditional extra request.

## Pagination and bounded windows

Lazada uses offset pagination for GetOrders: page size up to 100 and offset up to 5000. Offset is request-local and must never be a durable checkpoint.

The provider client must detect a window that can exceed the offset ceiling and split it by a verified time field. A split must be deterministic, preserve boundary records, exact-deduplicate by `order_id`, and fail coherently if a sub-window cannot be proven complete. It must not silently truncate at offset 5000.

Initial sync will use an explicit bounded create-time window once both boundaries are verified. There is no unbounded history default.

Incremental sync is provisionally designed around an updated-through watermark and deterministic `windowEnd`, with a provider-owned overlap policy. This is **UNRESOLVED** until `updated_after` and `updated_before`, boundary inclusivity, timestamp precision, and ordering are verified officially. Pagination offset is never the checkpoint.

## Order items and status

`GetOrderItems` (`/order/items/get`) obtains items for one order. `GetMultipleOrderItems` (`/orders/items/get`) is currently listed by Lazada as an available order API, but its accepted order-ID count and request/response batching limits are **UNVERIFIED**. Stage 14D.2/OrderClient work must inspect the live official API reference before selecting a batch size.

Lazada models each purchased unit as a separate order-item object with a unique `order_item_id`; buying two identical units can produce two item objects rather than one object with quantity two. A future normalizer must preserve provider item identity and may aggregate only if the canonical Ecomkit contract explicitly requires it and no information is lost.

Lazada does not expose one authoritative order status. Each item has its own status, and the order `statuses` array is the distinct collection of current item statuses. `LazadaNormalizer` therefore needs a documented, tested mixed-status policy. Until that policy is approved, it must preserve the full raw collection in provider metadata and must not select an arbitrary first status.

The order tutorial confirms order-level fields including `order_id`, `address_shipping`, `shipping_fee`, `statuses`, `price`, and `voucher`. API fixtures must verify `created_at`, `updated_at`, payment method, currency, and item field names (`order_item_id`, `sku`, `shop_sku`, `name`, `item_price`, `paid_price`) before mapping them. Unsupported or absent fields remain unset.

`updated_at` is the candidate for `providerUpdatedAt`, but its exact update semantics relative to item-status changes must be verified against the official API reference and synthetic fixtures. `Date.now()` is forbidden.

## Sensitive data

Buyer/order data can be masked by default. Lazada documents a Sensitive Data Privilege/DataMoat review for buyer personal information and other sensitive business data. Ecomkit must accept masked or absent buyer fields, preserve them as received in `rawData`, and leave normalized fields missing. It must never infer names, phones, or addresses or work around provider masking.

## Error and rate-limit model

Lazada responses are JSON. Failed calls include an error code and request ID. Official error guidance distinguishes platform/basic-verification errors, business-data errors, and backend availability errors. A future provider error should preserve safe `code`, `message`, `requestId`, operation, and an evidence-based retryable flag.

- Network timeout and documented backend availability errors may be retryable.
- Invalid signature, authorization, parameters, permissions, and business-rule errors are deterministic unless the specific official code says otherwise.
- Rate-limit retry behavior and exact QPS are **UNVERIFIED / app- and console-dependent**. Do not hardcode a quota or invent `Retry-After` behavior.

## Normalizer and adapter plan

`LazadaNormalizer` will be pure, deterministic, server-only, and free of DB, token, and network dependencies. It will consume validated order plus item snapshots and return the existing `NormalizedMarketplaceOrder`. It will map only verified fields and preserve missing values as missing.

`LazadaAdapter` fits MarketplaceAdapter V2 without a generic change:

```text
MarketplaceAdapterContext + MarketplaceAdapterSyncInput
  -> Lazada checkpoint/window resolver
  -> Lazada OrderClient (window splitting + offset pagination + item batching)
  -> LazadaNormalizer
  -> MarketplaceAdapterSyncResult
```

- The adapter owns list/detail/item orchestration, exact deduplication, pagination, normalization, and candidate checkpoint creation.
- `rawData` is the actual JSON-safe Lazada order-plus-item provider snapshot, not a reconstruction of normalized data.
- `normalizedData` is exactly the LazadaNormalizer result.
- Generic Worker continues to own persistence, stale-update policy, Batch bridge, retries, and checkpoint commit.
- The adapter result remains coherent all-or-error.

V2 already carries bounded initial windows, deterministic incremental upper bounds, opaque committed/candidate checkpoints, raw and normalized snapshots, and `providerUpdatedAt`. No generic contract change is required. Order implementation remains gated on verified update filters and update timestamp semantics.

## Credential architecture

Reuse the existing provider-neutral structures:

- `MarketplaceProviderConfig`: platform, region/environment, App Key, encrypted App Secret, redirect URI, enabled/audit state.
- `MarketplaceConnection`: region-qualified seller identity and encrypted token envelope.
- Existing AES-256-GCM credential envelope and runtime-only encryption key.
- Existing `CredentialSource=EXTERNAL_IMPORT` and `RefreshOwnership=EXTERNAL` metadata semantics.

For external read-only validation, import only same-App-Key App Secret, current access token, VN seller identity, and expiry. Do not import a refresh token. Ecomkit must fail before provider refresh if an externally owned token expires. No OAuth callback or public domain is required for this external mode.

It should expose configuration, token, live-test, connection, and sync-history statuses independently. It must never return or prefill secrets. No UI is implemented in this stage.

## Stage 14D.2 implementation record

The server-only `marketplace-server` workspace now exports a pure Lazada signer and a low-level HTTP client foundation. It does not load database configuration, persist tokens, implement OAuth, call an order endpoint, or register a Lazada adapter.

The signer:

- excludes an existing `sign` parameter and does not mutate caller input;
- omits undefined and empty-string values consistently with the official sample implementation;
- ASCII-orders parameter names, prefixes the API path, and appends an optional raw request-body string;
- applies HMAC-SHA256 with the App Secret and emits 64-character uppercase hexadecimal;
- emits common `app_key`, Unix-millisecond `timestamp`, `sign_method=sha256`, optional `access_token`, and the calculated `sign`;
- passes the complete official `/order/get` signing vector from Lazada documentation.

The HTTP core:

- keeps token (`https://auth.lazada.com/rest`) and Vietnam seller (`https://api.lazada.vn/rest`) targets distinct;
- accepts only GET/POST, explicit server-side credentials, an injectable clock, and an injectable transport;
- transmits the same API path, normalized parameters, and raw body string used by the signer;
- treats only provider code `0` (numeric or string) with HTTP 2xx as success;
- preserves safe provider code, sanitized provider message, request ID, HTTP status, operation, and API path;
- classifies timeout, network, and HTTP 5xx failures as retryable while provider auth/permission/parameter failures default to non-retryable;
- performs no internal retry and adds no rate-limit/QPS assumptions;
- excludes App Secret, access/refresh tokens, authorization-code-like parameters, and signatures from errors and diagnostics.

All transport tests are synthetic and make zero provider requests. The unresolved order/checkpoint facts listed above remain unresolved.
